# AI Interview Backend — текущий статус MVP

> Архивный снимок прежнего stateless MVP. Актуальный сквозной workflow и запуск
> описаны в `README.md` этого каталога и в корневом `README.md`.

Дата обновления: 4 сентября 2026 года.

## Краткий итог

Собран работающий backend-прототип для подготовки и проведения AI-интервью.

На текущий момент backend умеет:

- принимать резюме кандидата, вакансию и требования в PDF, DOCX или TXT;
- извлекать из документов текст без постоянного сохранения файлов;
- локально генерировать заданное количество основных и персонализированных вопросов;
- принимать аудиофайл ответа кандидата и расшифровывать его локально;
- возвращать унифицированные JSON-ответы и прикладные ошибки;
- предоставлять Swagger-документацию и health endpoint.

Все AI-модели работают локально. Платные внешние AI API и API-ключи не используются.

## Реализованные API

### `GET /health`

Проверяет доступность процесса FastAPI.

Успешный ответ:

```json
{
  "status": "ok"
}
```

### `POST /api/v1/questions/generate`

Принимает `multipart/form-data`.

Поля:

| Поле | Обязательность | Описание |
| --- | --- | --- |
| `cv` | нет | Резюме: PDF, DOCX или UTF-8 TXT |
| `vacancy` | нет | Описание вакансии: PDF, DOCX или UTF-8 TXT |
| `requirements` | нет | Требования: PDF, DOCX или UTF-8 TXT |
| `question_count` | да | Общее количество вопросов, от 1 до 20 |
| `core_question_count` | да | Количество основных вопросов |
| `language` | да | Язык результата, например `ru` или `en` |

Необходимо загрузить хотя бы один документ. Если запрошены основные вопросы,
нужно передать `vacancy` или `requirements`.

Документы обрабатываются только в рамках текущего HTTP-запроса. Backend не
создаёт для них постоянное файловое хранилище и не сохраняет их в базу данных.

Ответ содержит:

- уникальный ID вопроса;
- тип `core` или `personalized`;
- текст вопроса;
- проверяемую компетенцию;
- источники `cv`, `vacancy` и/или `requirements`.

Основные вопросы строятся только по вакансии и требованиям. Информация из CV
считается неподтверждённым заявлением кандидата и используется только в
персонализированных вопросах с формулировкой, требующей подтверждения.

Генерация выполняется локальной моделью `qwen3:4b` через Ollama. Для повышения
стабильности вопросы создаются небольшими однородными батчами: отдельно
основные и отдельно персонализированные, не более трёх за один вызов модели.
Backend собирает и валидирует итоговый список и возвращает только точное
запрошенное количество вопросов.

### `POST /api/v1/transcriptions`

Принимает `multipart/form-data`.

| Поле | Обязательность | Описание |
| --- | --- | --- |
| `audio` | да | Аудиофайл ответа кандидата |
| `language` | нет | Ожидаемый язык речи |
| `interview_id` | нет | Идентификатор интервью |
| `question_id` | нет | Идентификатор вопроса |

Пример ответа:

```json
{
  "text": "Распознанный ответ кандидата",
  "is_final": true,
  "question_id": "question-1",
  "meta": {
    "provider": "faster-whisper"
  }
}
```

Расшифровка выполняется локально через `faster-whisper`. По умолчанию
используется мультиязычная модель `small` в режиме `cpu/int8`.

Аудио передаётся провайдеру как seekable stream. Ручка не создаёт лишнюю полную
копию файла в памяти. Этот же сервис можно будет вызывать из будущего
WebSocket-адаптера.

## Архитектура

Backend разделён на слои:

```text
FastAPI routes
    ↓
application services
    ↓
provider protocols
    ↓
Ollama / faster-whisper / document parsers
```

Маршруты не обращаются напрямую к Ollama или faster-whisper. Настройки моделей,
таймаутов и лимитов загружаются из переменных окружения.

Основные абстракции:

- `QuestionGenerationProvider`;
- `TranscriptionProvider`;
- `DocumentTextExtractor`;
- `QuestionGenerationService`;
- `TranscriptionService`;
- `DocumentExtractionService`.

## Обработка документов

Поддерживается:

- PDF с текстовым слоем;
- DOCX, включая обычные абзацы и таблицы;
- TXT в UTF-8.

Пока не поддерживается:

- старый формат DOC;
- OCR изображений;
- сканированные PDF без текстового слоя;
- изображения резюме;
- защищённые паролем документы.

Текущие лимиты по умолчанию:

- один документ — до 10 МБ;
- извлечённый текст одного документа — до 100 000 символов;
- аудио — до 20 МБ;
- количество вопросов — до 20.

## Ошибки API

Backend возвращает единый формат ошибок:

```json
{
  "error": {
    "code": "error_code",
    "message": "Human-readable message",
    "details": null
  }
}
```

Основные статусы:

- `413` — превышен лимит размера;
- `415` — неподдерживаемый тип документа;
- `422` — некорректный запрос, пустой документ или неразбираемый файл;
- `502` — модель вернула результат, который не удалось привести к контракту;
- `503` — локальный AI-провайдер недоступен;
- `504` — превышен таймаут провайдера.

## Текущие ограничения и риски

1. `qwen3:4b` — небольшая модель. Качество вопросов зависит от входных
   документов, а генерация 10 вопросов выполняется несколькими вызовами и может
   занимать десятки секунд.
2. При CPU-инференсе генерация и транскрипция могут быть медленными.
3. Нет OCR для сканированных PDF.
4. Нет WebSocket и частичных результатов транскрипции.
5. Нет авторизации, ролей пользователей и rate limiting.
6. `/health` проверяет FastAPI, но пока не проверяет готовность Ollama и Whisper.
7. Нет метрик, централизованных логов и tracing.
8. Нет постоянного хранения интервью, вопросов и транскрипций.
9. Нет готового deployment-пакета, CI и конфигурации reverse proxy.
10. Ollama API нельзя публиковать напрямую в интернет: она должна оставаться во
    внутренней сети или слушать только loopback-интерфейс.

## Готовность

### Для локального или внутреннего demo-стенда

Готово после:

- размещения проекта в Git;
- установки зависимостей на VM;
- предварительного скачивания `qwen3:4b` и Whisper `small`;
- настройки запуска FastAPI и Ollama как сервисов;
- smoke-теста с реальными документами и аудио.

### Для публичного production

Пока не готово. Минимально потребуются:

- HTTPS и reverse proxy;
- аутентификация и авторизация;
- закрытый доступ к Ollama;
- rate limiting и ограничения конкурентных запросов;
- readiness-проверки AI-провайдеров;
- мониторинг и централизованные логи;
- нагрузочное тестирование на целевом оборудовании;
- стратегия хранения и удаления персональных данных;
- зафиксированные версии runtime и моделей;
- CI/CD и воспроизводимый deployment.

## Рекомендуемые ближайшие шаги

Приоритет перед передачей команде и запуском стенда:

1. Создать приватный Git-репозиторий и `.gitignore`.
2. Добавить инструкцию развёртывания для целевой Ubuntu VM.
3. Добавить systemd unit для FastAPI; Ollama также запускать через systemd.
4. Не открывать порт Ollama `11434` в публичный интернет.
5. Для внутреннего тестирования использовать SSH-туннель либо HTTPS reverse proxy.
6. Предварительно загрузить обе модели до запуска приложения.
7. Выполнить smoke-тест транскрипции с реальным WAV/MP3/WEBM.
8. Проверить два параллельных запроса и подобрать VM по фактической задержке.
9. Согласовать срок хранения документов, вопросов и транскрипций.
10. После demo определить, достаточно ли качества `qwen3:4b` или нужна более
    сильная модель.
